# Architecture Options

Stage: Discovery documentation. Constraints from the brief: static GitHub Pages hosting, no
production backend, no secrets or paid feeds, browser-local processing of uploads, presentation-
ready on a conference screen, auditable by an analyst.

## Excel-first bridge (decided before any web work)

The expanded workbook is the system of record for the demo dataset and calculations. The web
prototype consumes a **normalized export table** generated by the workbook — it never scrapes
presentation cells. This keeps the analyst-auditable artifact (Excel) and the presentation
artifact (web) in lockstep through one documented interface.

## Web stack options compared

| Option | Pros | Cons |
|---|---|---|
| **1. Vite + React 18 + TypeScript (strict) SPA** | Schema-first typing end to end; Vitest for pure calculation modules; mature accessibility patterns; largest maintainer pool; trivial Pages deploy | Bundle larger than option 2; React overhead for a mostly-static UI |
| 2. SvelteKit (static adapter) | Smallest output; elegant reactive tables | Smaller talent pool for a public-pension team to maintain; fewer battle-tested a11y component patterns |
| 3. No-framework TypeScript + Lit/web components | Minimal footprint; no framework churn | Slowest path to polished loading/empty/stale/error states; hand-rolled routing and focus management |

**Recommendation: Option 1** — Vite + React + TypeScript (strict), with:

- **Zod** schemas as the single source of validation truth at the import boundary (fixtures and
  user CSV imports go through the same parser).
- **Pure calculation modules** (`src/lib/finance/*`): no React imports, fully unit-tested
  (Vitest) — return compounding, contribution + reconciliation, allocation variance, staleness.
- **PapaParse** for CSV import in the browser (FileReader; no network).
- **Recharts** for the small number of charts that earn their place; everything else is
  accessible HTML tables.
- **React Router with `basename`** (or hash routing fallback) so deep links work on a
  project-site base path (`/<repo>/`).
- **No telemetry, no analytics, no external fonts/CDNs** — everything bundled.

## Hosting

GitHub Pages project site via the standard `actions/deploy-pages` workflow (no Anthropic key, no
custom action). `vite.config.ts` `base` set to the repository name. A `404.html` copy of
`index.html` (or hash routing) covers deep-link refresh. All alternatives (Netlify, Cloudflare
Pages) also satisfy the constraints; GitHub Pages is chosen because the repository already lives
on GitHub and requires no third-party account.

## Explicitly rejected

- Any backend, database, serverless function, or scheduled ingestion (future-state only).
- Claude Code Action / Anthropic API key in CI merely to deploy a static site.
- Client-side fetches to market-data APIs (would need keys and violate the no-secrets rule).
